# ADR-0004：跨服务审计——网关唯一发射 + 独立 audit-service

- 状态：已接受
- 日期：2026-08-02

## 背景

需求是"审计要覆盖多服务"（登录、RBAC 变更、客户增删改、审批、admin 直删都要可追溯）。两个候选方案被否决：

- **塞进某个 domain 服务**：各写各的、口径不一，且审计横切基础设施，不该属于任何业务域。
- **独立审计服务落在写操作关键路径**：每次删除先写审计，就得回答"审计挂了业务还做不做"——fail-closed 变可用性炸弹，fail-open 又让日志不可靠。

## 决策

**网关为唯一发射点 + 独立 audit-service（4104，第 7 个服务）**：

- 所有业务调用都过网关，PEP 裁决后天然知道：谁（`X-User`）、对什么资源、什么动作（permission）、放行还是拒绝。在网关统一发射即可零侵入覆盖所有服务，业务服务完全不用改。
- **异步 best-effort**：`WebClient` 非阻塞 post 到 `lb://audit-service/api/audit`，`subscribe()` 不阻塞主流程；发射失败只记本地日志、绝不抛异常 → **fail-open**，审计服务挂了不影响业务。
- **写端点防伪造**：`POST /api/audit` 仅接受网关经服务发现直连且带私有头 `X-Internal-Audit: gateway`，否则 400。外部只能读。
- **读端点**：`GET /api/audit`（分页 + 统计 + 筛选）走网关、需 `audit:read`（仅 admin）。
- **append-only**：无更新/删除端点。
- 公开路由（login/register）不审计；认证失败记 `auth:missing/invalid`（DENY）。

## 后果

- 审计覆盖所有经网关的请求，含 admin 直删、审批通过/驳回——业务代码零改动即获全链路可追溯。
- 审计服务故障不影响业务（fail-open），代价是极端情况下日志可能缺失（可接受）。
- 日志量与全站 QPS 成正比 → 必然要分页 + 统计汇总（Audit 面板：今日操作/拒绝/活跃用户 + 只看拒绝/删除筛选）。
- H2 独立库 + `ddl-auto=update` 使日志跨重启持久化（ADR-0005）。
